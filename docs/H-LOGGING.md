## Lock

H-4 rewrote this Lock on 2026-10-19, before any code. Until H-4 lands, the code still writes `logs/<id>.log` as H-1 to H-3 built it. The bullets below are the contract H-4 builds.

- **SQLite is the record. There are no log files.** Each profile has its own log database, `log.db`, next to the profile store (B Lock layout): `<profile id>.log.db`, named by the profile's `logs` key. Only the log thread opens it, on its own read-write connection. It does not go through the store writer. This is the one exception to the one-store-writer rule ([L-STORE.md](L-STORE.md) Lock), and it covers `log.db` only: the log thread never opens the profile store, and the store writer never opens `log.db`. Keeping them apart avoids the store-writer/activity-write deadlock and keeps log churn out of the mail database's WAL. The file is `0600` in a `0700` directory, `journal_mode=WAL`. Command handlers that read history (`log.query`, `log.export`) post to the log thread and get the rows back; they do not open `log.db` themselves. The view never opens the database.
- Schema (approved 2026-10-19, session table included): table `log (seq INTEGER PRIMARY KEY, ts INTEGER NOT NULL, session INTEGER NOT NULL, level INTEGER NOT NULL, subsystem TEXT NOT NULL, text TEXT NOT NULL)`. `ts` is UTC milliseconds. `level` is `PAV_ERROR` 0 to `PAV_DEBUG` 3. Indexes: `log_ts (ts)` for retention, and `log_session_seq (session, seq)` for the session filter and paging. Table `session (id INTEGER PRIMARY KEY, started INTEGER NOT NULL, source TEXT NOT NULL, label TEXT)`: one row per run (`source` `run`), and one per imported file (`source` `import`, `label` the file name). `log.db` has its own `user_version` and its own embedded migrations (`core/src/migrations/log/`), run by the log thread at open. A `log.db` newer than the binary is an error that leaves logging on stderr and the ring.
- `seq` is one counter per profile, across runs (approved 2026-10-19): the `log.db` primary key. The ring, `log.tail`, `log.lines`, and `log.query` all carry that same `seq`. Lines logged before the profile attaches take provisional numbers. At attach the log thread opens `log.db`, takes `max(seq)+1` as the base, renumbers the waiting ring lines in order, writes them, and only then posts their first `log.lines` batch. A start that never attaches (state `error`) keeps the provisional numbers and writes nothing.
- The core keeps the last 10,000 lines in an in-memory ring (`core/src/logring.c`) as the live cache, filled by the log thread. `log.tail` reads the ring, as it does now. The ring holds the same lines as `log.db`.
- Every line is also delivered as an event: the log thread emits `log.lines {lines:[{seq, ts, level, subsystem, text}, ...]}` through `pav_on_event`, at most one batch per 100 ms. There is no per-line `log.line` event. H-4 does not change this event. From H-4, `log.lines` has a real `### log.lines` heading in [API.md](API.md). That reverses the H-1 to H-3 Handoff rule "do not add a `### log.lines` heading". Those Handoff lines stay as history.
- Pre-attach lines: a line logged before any workdir exists goes to stderr at every level, because stderr is the only record. A line logged after the workdir is known but before the profile attaches waits in the ring, and only `WARN` and `ERROR` also go to stderr. When `log.db` attaches, those lines are written at once, each exactly once. Nothing is lost or duplicated.
- Writes: the log thread batches rows into one transaction about every 100 ms. An `ERROR` line waits for its commit: `pav_log` at `ERROR` returns once the log thread has committed that line and everything queued before it, or after about 250 ms, whichever comes first, and then returns anyway; the line stays queued and is committed with the next batch (a caller on the log thread writes it directly). `pav_log_thread_shutdown` flushes and commits everything before it closes `log.db` and joins.
- stderr: `WARN` and `ERROR` go to stderr at all times, before and after attach ([C-CORE.md](C-CORE.md) Logging). The one exception is before any workdir exists, when stderr is the only record and gets every level. `INFO` and `DEBUG` otherwise stay in `log.db` and the ring. There is no `logs/` directory and no `pavillion.log`.
- Retention: keep 30 days or 1,000,000 rows, whichever is smaller. The log thread trims at attach and then hourly, oldest `seq` first, and drops `session` rows with no lines left. This replaces the 10 MB `<id>.log.1` rename (H-Q1).
- One-time import (scope approved 2026-10-19): at the first attach of a profile whose `log.db` is new, its old files in the workdir's `logs/` (`<profile id>.log.1`, then `<profile id>.log`, then the shared pre-profile `pavillion.log` on the first profile that attaches) are parsed as C-CORE lines and inserted in file order, each file under its own `session` row (`source` `import`, `label` the file name). Another profile's files wait for that profile's first attach. A line that does not parse is imported as `INFO`, subsystem `import`, with the raw text. After the import commits, those files are deleted, and `logs/` is removed once it is empty. A failed import leaves the files in place and logs one `WARN`.
- Reading history: `log.query {beforeSeq?, limit, levels?, subsystems?, text?, session?}` reads `log.db` newest first below `beforeSeq` and returns the page oldest first, in the `log.tail` row shape. `session` is `current`, `previous`, `all` (default), or a session id. Scrolling above the oldest loaded line pages older lines in through `log.query`. The view has a session filter: This run, Last run, All. `log.tail` stays the ring and is unchanged. Copy, Save, and Print use the same `log.query` filter. `log.export {path, filter}` writes its lines from `log.db`, as C-CORE lines with UTC stamps. Filtering of loaded lines is still client-side; `log.tail` and `log.query` filter in the core when asked.
- Times on screen are local `HH:mm:ss.mmm` (24 h, profile timezone, default `America/Vancouver`). Hovering a line shows the UTC stamp. `log.db` and exports stay UTC.
- Levels: `log_level` stays on the index (`error`, `warn`, `info`, `debug`) as the default minimum. H-4 adds a per-subsystem minimum in the profile, `preferences.log_levels` (an object of subsystem name to level, B Lock), which overrides the default for that subsystem (H-Q2). The gear in the Log view and Settings both edit it. `prefs.set {logLevel}` still sets the session default and writes the index.
- Nothing bypasses `pav_log`. C `fprintf(stderr, ...)`, Rust `eprintln!` and `println!`, JS `console.warn` and `console.error` (through `log.client`), and plugin output are routed through it. The only exceptions are output written before the core can log: `--help`, `--version`, the F-1 `API version mismatch` line, and `pav_log`'s own stderr copy. A test lists the allowed call sites and fails on any new one.
- Redaction (was plan §11): never log a password, token, `Authorization` header, cookie, message body, or bot key. Log ids, sizes, counts, durations, and HTTP status. `pav_log` callers pass ids, never content. A Unity test (`test_log_redacts_known_secret_shapes`) feeds a fixture `Authorization: Basic …` and `Bearer …` through the HTTP debug path (M-1) and asserts neither appears.
- The viewer is CodeMirror 6 (`@codemirror/view`, `@codemirror/state`, `@codemirror/search`), read-only, installed in H-2 and bundled by Vite. The same packages later edit HTML (F-8) and Lua (R-4). The document is plain text. Level color is a line decoration, not HTML in the document. Font is the monospace already used by the shell (Vanadium Mono when installed, then `ui-monospace, monospace`); G-4 and D-4 keep that choice when they name `--pav-font-mono`. The document starts as the ring and grows upward as history pages in from `log.db` (H-4). CodeMirror virtualizes the viewport. Copy, Save, and Print take their lines from the same `log.query` the view used, as UTC C-CORE lines. The on-screen timestamp is local time.
- H-2 creates the Log view and the `Activity | Log` segmented control on the Activity tab, before I-2 and before J-1. The Activity side stays empty until I-2. The right-click menu on the Activity nav button is J-1; it switches the two views H-2 already created. Plain click opens the last view used (`preferences.ui.activity.view`, default `log` until I-2).
- H-2 runs before G-4. It adds `--pav-log-error`, `--pav-log-warn`, `--pav-log-info`, and `--pav-log-debug` to the current theme files and uses those names. G-4 keeps them when it renames the older properties. Do not wait on G-4 to show the log.
