## Lock

H-4 rewrote this Lock on 2026-10-19, before any code. Until H-4 lands, the code still writes `logs/<id>.log` as H-1 to H-3 built it. The bullets below are the contract H-4 builds.

- **SQLite is the record. There are no log files.** Each profile has its own log database, `log.db`, next to the profile store (B Lock layout): `<profile id>.log.db`, named by the profile's `logs` key. Only the log thread opens it, on its own read-write connection. It does not go through the store writer. This is the one exception to the one-store-writer rule ([L-STORE.md](L-STORE.md) Lock), and it covers `log.db` only: the log thread never opens the profile store, and the store writer never opens `log.db`. Keeping them apart avoids the store-writer/activity-write deadlock and keeps log churn out of the mail database's WAL. The file is `0600` in a `0700` directory, `journal_mode=WAL`. Command handlers that read history (`log.query`, `log.export`) post to the log thread and get the rows back; they do not open `log.db` themselves. The view never opens the database.
- Schema (approved 2026-10-19, session table included): table `log (seq INTEGER PRIMARY KEY, ts INTEGER NOT NULL, session INTEGER NOT NULL, level INTEGER NOT NULL, subsystem TEXT NOT NULL, text TEXT NOT NULL)`. `ts` is UTC milliseconds. `level` is `PAV_ERROR` 0 to `PAV_TRACE` 4. Indexes: `log_ts (ts)` for the view's time range, `log_session_seq (session, seq)` for the session filter and paging, and `log_level_seq (level, seq)` so a filtered page stays cheap at TRACE volume. Table `session (id INTEGER PRIMARY KEY, started INTEGER NOT NULL, source TEXT NOT NULL, label TEXT)`: one row per run (`source` `run`). `log.db` is created with `auto_vacuum=INCREMENTAL`, has its own `user_version` and its own embedded migrations (`core/src/migrations/log/`), run by the log thread at open. A `log.db` newer than the binary is an error that leaves logging on stderr and the ring.
- `seq` is one counter per profile, across runs (approved 2026-10-19): the `log.db` primary key. The ring, `log.tail`, `log.lines`, and `log.query` all carry that same `seq`. Lines logged before the profile attaches take provisional numbers. At attach the log thread opens `log.db`, takes `max(seq)+1` as the base, renumbers the waiting ring lines in order, writes them, and only then posts their first `log.lines` batch. A start that never attaches (state `error`) keeps the provisional numbers and writes nothing.
- The core keeps the last 10,000 lines in an in-memory ring (`core/src/logring.c`) as the live cache, filled by the log thread. `log.tail` reads the ring, as it does now. The ring holds every level, `TRACE` included, the same lines as `log.db`; it stays the live cache (revised 2026-10-19: no level floor).
- Every ring line is also delivered as an event: the log thread emits `log.lines {lines:[{seq, ts, level, subsystem, text}, ...]}` through `pav_on_event`, at most one batch per 100 ms, every level. The 100 ms batching is the burst control. There is no per-line `log.line` event. From H-4, `log.lines` has a real `### log.lines` heading in [API.md](API.md). That reverses the H-1 to H-3 Handoff rule "do not add a `### log.lines` heading". Those Handoff lines stay as history.
- Pre-attach lines: a line logged before any workdir exists goes to stderr at every level, because stderr is the only record. A line logged after the workdir is known but before the profile attaches waits in the ring only; nothing goes to stderr (Andrew, 2026-10-19: logs go to the database only). When `log.db` attaches, those lines are written at once, each exactly once. Nothing is lost or duplicated. At most 10,000 lines wait (the ring size); past that the oldest waiting lines are dropped from the wait (2026-10-19, commit 2).
- Writes: the log thread batches rows into one transaction about every 100 ms. An `ERROR` line waits for its commit: `pav_log` at `ERROR` returns once the log thread has committed that line and everything queued before it, or after about 250 ms, whichever comes first, and then returns anyway; the line stays queued and is committed with the next batch (a caller on the log thread writes it directly). `pav_log_thread_shutdown` flushes and commits everything before it closes `log.db` and joins. `pav_log_set_output` stays as a test-only text sink: while it is set, lines go to that file and the ring, not to stderr or `log.db` (2026-10-19, commit 2).
- stderr (Andrew, 2026-10-19, replaces the WARN and ERROR copy): once a workdir is known nothing is copied to stderr at any level; lines go to the ring and `log.db` only. stderr carries a line only when there is no database to hold it: before any workdir exists, and when `log.db` cannot be opened (both every level), plus the second-launch line (O Lock). A Unity test fails if a `WARN` or `ERROR` after the workdir reaches stderr. There is no `logs/` directory and no `pavillion.log`.
- Retention (approved 2026-10-19, replaces the 30 days / 1,000,000 rows rule and H-Q1's rename): one size cap for all levels, no age limit. The profile key `preferences.log_max_mb` (B Lock) is an integer from 1 to 100, default 10. Size is measured as `(page_count - freelist_count) * page_size` of `log.db`; WAL and shm files are not counted (they are checkpointed at shutdown). Trimming deletes the oldest `seq` first in chunks of at most 1,000 rows (each chunk sized from the average row, so a cap is not undershot by a whole chunk; 2026-10-19, commit 2) until the measured size is at or under the cap, drops `session` rows with no lines left, then runs `PRAGMA incremental_vacuum` so the file shrinks. It runs at shutdown (after the last flush, before close) and on `log.trim`. There is no trim at attach and no hourly trim. Accuracy: the measure is exact for pages in use; after trimming, the file is within a few pages of the cap, and an index page that is still partly used can keep the file a little above it until the next trim.
- Commands (H-4, [API.md](API.md)): `log.stats {}` returns `{bytes, records, oldestSeq, oldestTs, capMb}` from `log.db`. `log.trim_preview {mb}` deletes nothing and returns `{bytes, records, oldestTs}` as they would be after trimming to `mb`: it estimates each row's share as `length(text) + length(subsystem) + 24` bytes, scales the estimates so they sum to the measured size, and walks newest first until the cap. The preview is an estimate (expect within about 10 % on ordinary lines); `log.stats` after Apply is the measured truth. `log.trim {mb?}` with `mb` writes `preferences.log_max_mb`, trims to it now, and returns `log.stats`; without `mb` it trims to the saved cap, writes nothing, and returns `log.stats` (Trim Now). Both use the same trim path as shutdown. All three run on the log thread. `mb` outside 1 to 100 is `bad_args`.
- Settings (the log settings area): a slider from 1 to 100 MB showing the cap; a Refresh button that shows the current storage used (MB), the record count, and the oldest record's local date and time (`log.stats`); moving the slider shows the preview for that cap (`log.trim_preview`); Apply calls `log.trim {mb}` and then shows the new stats. A Trim Now button calls `log.trim {}` to trim to the saved cap with no slider change, then shows the resulting size, records, and oldest record (for example 12 MB used with a 10 MB cap becomes at most 10 MB).
- Old files (approved 2026-10-19, replaces the one-time import): at the first attach of a profile, the old `logs/<profile id>.log`, `logs/<profile id>.log.1`, and the shared `logs/pavillion.log` are deleted without importing, and `logs/` is removed once empty. A failure to delete logs one `WARN` and leaves the file.
- Reading history: `log.query {beforeSeq?, since?, until?, limit, levels?, subsystems?, text?, session?}` reads `log.db` newest first below `beforeSeq`, within `since <= ts < until` (UTC ms, either omitted is open) through the `log_ts` index, and returns the page oldest first, in the `log.tail` row shape. `session` is `current`, `previous`, `all` (default), or a session id. Scrolling above the oldest loaded line pages older lines in through `log.query`. The view has a session filter: This run, Last run, All. `log.tail` stays the ring and is unchanged. Copy, Save, and Print use the same `log.query` filter. `log.export {path, filter}` writes its lines from `log.db`, as C-CORE lines with UTC stamps. Filtering of loaded lines is still client-side; `log.tail` and `log.query` filter in the core when asked.
- Time range (approved 2026-10-19; built in commit 3 with the view and history): the Log view shows a time range, default the last 12 hours. Presets are 1 h, 3 h, 6 h, 12 h, 24 h, 7 d, and All, plus Custom (two local date-time fields); no other choices (1 h, 3 h, and 6 h added 2026-10-19, Andrew). The initial load and the live view cover only that range: the view loads the ring lines inside it, and `log.lines` appends live lines as they come. Older lines are read from `log.db` through `log.query {since, until}` only when the user widens the range or scrolls above the oldest loaded line. The ring stays the live cache and is never the history. The range is a view setting kept in `preferences.ui.log.range` (`1h`, `3h`, `6h`, `12h` default, `24h`, `7d`, `all`, or `{since, until}`). The session choice (This run, Last run, All) persists the same way in `preferences.ui.log.session` (`current`, `previous`, `all`; default `all`) (Andrew, 2026-10-19).
- Times on screen are the Formats `timeSeconds` string (default `HH:mm:ss.SSS`, 24 h) in the profile timezone (`prefs.get` `timezone`), else the system zone, else `America/Vancouver`. The CodeMirror document holds that display line; hovering a line shows the UTC stamp. `log.db` stores UTC ms. Copy, Print, and Save use that same display line (Andrew, 2026-10-23, D-8). Save writes it through `export.write_text`. The core command `log.export` still writes C-CORE lines with UTC stamps, because the core does not read `preferences.ui` and does not format dates. (The screen time was local `HH:mm:ss.mmm` from H-4 commit 4, 2026-10-19, until D-8.)
- Levels (approved 2026-10-19): `PAV_ERROR` 0, `PAV_WARN` 1, `PAV_INFO` 2, `PAV_DEBUG` 3, `PAV_TRACE` 4. Every level is captured, always: nothing is discarded by level when a line is logged. `log_level` stays on the index (`error`, `warn`, `info`, `debug`, `trace`) and is only the Log view's default level filter, default `info`; the view's level checkboxes start at that level and above. `prefs.set {logLevel}` writes the index and does not change what is captured. H-Q2's `preferences.log_levels` is dropped as redundant: with every level captured, the view's level and subsystem filters already decide what is shown.
- Level policy. `ERROR`: an operation failed and the user loses something or must act (store write failed, `log.db` cannot open, 401 stopped an account). `WARN`: degraded but recovering (keyring locked, retry scheduled, profile file ignored, slow command). Slow command: a local command over 250 ms is one `WARN`. Network-bound commands (`account.test`, `account.discover`, and later sync and send commands, marked in the dispatcher table) are `WARN` only past 10 s; under that their duration is a `DEBUG` line (Andrew, 2026-10-19). `INFO`: lifecycle and user-visible or user-initiated actions (start, stop, profile attach, window shown, account add, update, remove, test, a pref changed, activity begin and end, sync started and finished). `DEBUG`: internal steps (migrations, store open, net thread start and stop, Session parsed, redirect followed). `TRACE`: per request, per row, per tick (each HTTP transfer, each dispatched command, writer batches, per-row upserts).
- Repeats collapse (Andrew, 2026-10-19): a line identical to the previous one (same level, subsystem, and text after redaction) is not stored, put in the ring, sent on `log.lines`, or copied to stderr. The repeats are counted. When a different line arrives, after 1 s with no new line, on `pav_log_flush`, and at shutdown, one line goes out at the same level and subsystem: `previous line repeated N times`. ERROR lines collapse too; only the first waits for its commit. The next identical line after that summary starts a new run. `log.*` commands are not traced by dispatch at all.
- Session separators (Andrew, 2026-10-19): where the session id changes between two adjacent lines on screen, the view draws a divider row (a CodeMirror block widget, not a document line) labelled `Session <id> · started <local date and time>` (the Formats `datetime` string from D-8); the session's own first lines (`started: api …, <build> build`, `profile … attaching`, `core ready`) follow it. It uses the theme variables `--pav-border` (the rule) and `--pav-log-debug` (the label). It is screen-only: Copy, Save, and Print carry the display lines and no separator. `log.export` still carries the UTC lines and no separator. `log.query` rows carry `session`, and the result adds `sessions` (id to start, UTC ms) and `currentSession`; live ring lines are the current session. The first load for Session All or Last run reads `log.query` for the saved range, then follows live lines; This run starts from the ring.
- UI forwarding: the UI forwards user actions at `INFO` and navigation (tab, pane, view changes) at `DEBUG` through `log.client`, rate-limited to 50 lines per second; lines over the limit are dropped and counted into one `WARN` line per second.
- Nothing bypasses `pav_log`. C `fprintf(stderr, ...)`, Rust `eprintln!` and `println!`, JS `console.warn` and `console.error` (through `log.client`), and plugin output are routed through it. The only exceptions are output written before the core can log: `--help`, `--version`, the F-1 `API version mismatch` line, `pav_log`'s own stderr copy (only when no database can hold the line), and the second-launch line (Andrew, 2026-10-19: `Pavillion is already running for this profile; bringing it to the front.`, printed by a refused second launch, which never attaches a profile). A test lists the allowed call sites and fails on any new one. Known framework noise is mapped, not hidden: `[TAURI] Couldn't find callback id …` (a late event or reply after a view closed) goes to `DEBUG ui` as `late reply ignored after a view closed`; any other `[TAURI] …` stays `WARN`.
- Redaction (was plan §11, extended 2026-10-19): never log a password, token, `Authorization` header, cookie, message body, or bot key; never a pref value whose key names a secret (`secret`, `password`, `token`, `key`); never a URL query string; at `INFO` an email address appears only as the account id (the address itself at `DEBUG` or below). Log ids, sizes, counts, durations, and HTTP status. `pav_log` callers pass ids, never content. A Unity test (`test_log_redacts_known_secret_shapes`) feeds a fixture `Authorization: Basic …`, `Bearer …`, a URL with a query, and a secret-named pref through the paths that log them and asserts none appears.
- The viewer is CodeMirror 6 (`@codemirror/view`, `@codemirror/state`, `@codemirror/search`), read-only, installed in H-2 and bundled by Vite. The same packages later edit HTML (F-8) and Lua (R-4). The document is plain text. Level color is a line decoration, not HTML in the document. Font is the monospace already used by the shell (Vanadium Mono when installed, then `ui-monospace, monospace`); G-4 and D-4 keep that choice when they name `--pav-font-mono`. The document starts as the ring and grows upward as history pages in from `log.db` (H-4). CodeMirror virtualizes the viewport. Copy and Print take the visible display lines. Save pages `log.query` with the view's filter and writes those display lines through `export.write_text`. The on-screen timestamp is the Formats `timeSeconds` string.
- H-2 creates the Log view and the `Activity | Log` segmented control on the Activity tab, before I-2 and before J-1. The Activity side stays empty until I-2. The right-click menu on the Activity nav button is J-1; it switches the two views H-2 already created. Plain click opens the last view used (`preferences.ui.activity.view`, default `log` until I-2).

It adds `--pav-log-error`, `--pav-log-warn`, `--pav-log-info`, and `--pav-log-debug` to the current theme files and uses those names; `TRACE` lines use the `DEBUG` styling (`--pav-log-debug`), with no variable of their own. Two sentences in Done means were superseded by the Lock before the code: a per-subsystem debug level was dropped (`preferences.log_levels`), and old files are deleted rather than imported.

**Lessons learned:** Capture every level and let the view filter. A per-subsystem floor was specified, then dropped, because the database is the record and the screen is the filter. Retention is one size cap, trimmed at shutdown and on demand, not a day count or a row count. Importing old text logs was dropped the same way: delete them. TRACE is an ordinary level with DEBUG styling. A separate `--pav-log-trace` was not added. The on-screen document is the local 24-hour line. Copy and save stay the UTC bytes. Consecutive identical lines belong in `pav_log`, not in each caller. Redaction has to live in `pav_log` itself or `log.client` walks around it. `pav_jmap_post` must keep the session URL on the context. A stack buffer becomes a dangling pointer after the call returns. The ring is still the live cache. History is `log.query` against `log.db`, posted to the log thread. Command handlers do not open that file.
